# 财务人生推演 v1：规则与数据结构

状态：供实现与评审的规则定稿草案  
范围：使用已确认财务画像与已选规划，点击推进一段假设性的财务人生。本文只规定规则和数据契约；页面、事件内容、计算引擎、数据库迁移均不在本轮实现范围。类型契约见 [`financial-life-simulation.types.ts`](../src/domain/financial-life-simulation.types.ts)。

## 1. 产品边界与基本单位

- 一局以一个目标、一个已选 Plan A/B/C、一个底账版本为起点。默认从**当前日期的下一个完整自然月**开始，到目标月份末结束；上限暂定 240 个月。目标已到期则不能开局。
- 界面一次点击推进至下一自然年末，或提前停在重大事件、现金缺口、目标到期月份。引擎始终**逐月**结算；年度故事卡是月度结果的摘要。
- `monthIndex = 0` 表示开局第一个月；界面显示“第 1 个月”。所有事件配置使用 `YYYY-MM`，不混用零基/一基的发生月份。
- 默认 `OBSERVE`：用户开局后只需点“进入下一年”。`SPECIFIED_SCENARIO` 保留用户指定事件入口。两种模式共用状态与结算规则。
- 现有画像只有整数年龄而无生日，因此模拟年龄按 `期初年龄 + 已完成的整年数` 估算，界面写“约 X 岁”；不得生成具体生日。
- 所有事件都是**情景假设**，不是现实事件概率或未来预测。随机权重只用于从合格候选事件中选择虚构剧情。
- 原始底账、目标和已选规划始终只读；模拟中的任何数值变化只能写入本局状态。

## 2. 开局快照：从现有数据映射

开局时冻结 `workspaceId`、`portfolioRevision`、`planSetId`、`planKey`、`goalId`、数据采集时间、规则版本、事件库版本和随机种子。后续底账变化使历史局标为 `STALE`，但历史结果不被静默改写。

| 本局字段 | 现有来源 | 规则 |
|---|---|---|
| 年龄、家庭状态 | `Profile` | 可为空；为空时相关事件不进入候选池，不凭空推断 |
| 稳定收入、其他收入 | `Profile` | 取已确认月度金额，合计为基准月收入 |
| 必需支出 | 房租、交通、基本支出 | 按现有字段汇总 |
| 可选支出 | 现有画像尚无直接字段 | 开局需用户确认金额；确认 0 才能用 0，未知不能自动置 0 |
| 可动用现金 | 未绑定目标且流动性为 T0/D7/D30 的资产 | 不计入目标专款；高风险或长期资产不自动出售 |
| 目标已准备资金 | `Goal.preparedAmountMinor` 与目标绑定资产 | 必须确定两者是否重叠，详见下段 |
| 其他资产 | 除可动用现金与目标绑定资产以外的资产 | 默认维持名义价值；无收益率、价格增长的隐含假设 |
| 负债 | 各 `Liability` | 保留每笔余额与月供，不能只用总额替代 |
| 目标与月投入 | 已选方案与目标 | 锁定目标金额、目标月份、计划月投入和弹性标记 |

### 目标资金去重

`Goal.preparedAmountMinor` 是用户填报的“已准备金额”，绑定目标的 `Asset` 是底账资产。若二者含有同一笔钱，直接相加会高估目标进度。创建本局前要求用户在三种口径中确认一种：

1. `LINKED_ASSETS_ONLY`：只以目标绑定资产计入期初目标进度；填报金额作为参考。
2. `DECLARED_ONLY`：只以填报金额计入期初目标进度；绑定资产不再额外相加。
3. `CONFIRMED_DISJOINT`：用户确认二者互不重叠，才可相加。

若有两种非零来源而尚未确认，不能计算目标进度。期初可动用现金必须排除目标绑定的流动资产。填报的已准备金额只用于目标进度，不自动变成另一笔可花的现金。v1 **不展示模拟净资产**，直到这笔金额与底账资产的关系能完整对账。

开局转换器将选定口径计算为 `initialGoalFundedMinor`，同时保留两项原始金额及口径供追溯。真实开局的 `source.kind` 为 `REAL` 并记录底账、方案与目标 ID；固定示例人生使用 `DEMO` 和示例版本 ID，不伪造财务空间或方案 ID。

### 数据校验

- 金额均为十进制整数形式的“分”字符串，人民币单币种；计算时转 `bigint`，不得经由 JavaScript 浮点数进行货币运算。
- 开局月、目标月为有效 `YYYY-MM`，目标月不早于开局月，跨度不超过 240 月；目标金额必须大于 0，收入、支出、资产、负债与计划投入不得为负。
- 事件造成负收入、负支出、负资产价值或非正目标金额时，事件配置无效，不能靠运行时静默截断为 0。
- 必需支出、可选支出、月供、收入是否真实为 0 需以用户确认状态判定，不能仅由数据库默认值推断。
- 不存在已选且未过期方案时，提示先完成规划；关键金额未知时只询问缺失项。年龄和家庭状态可以未知，但对应事件自动失去资格。

## 3. 一个月的确定性结算顺序

下列顺序固定，事件触发和现金缺口才可复现：

1. **取得月初状态。** 清理上月结束的临时效果，读取本月仍有效的收入/支出变化；同类效果冲突时，先按发生时间排序，后发生的 `MONTHLY_INCOME_OVERRIDE` 覆盖前者，支出增量相加。
2. **确定本月事件。** 先放入已到期的确定节点与用户确认事件，再评估条件事件，最后从探索事件池抽取。事件的效果从本月起生效；同月事件按“确定节点 → 用户确认 → 条件 → 探索”顺序执行。目标金额变更等状态效果先应用，随后结算财务账本。
3. **确认收入。** `收入 = 稳定收入 + 其他收入`，再应用本月有效的收入覆盖。覆盖不得令总收入小于 0。
4. **支付刚性需求。** 顺序为必需支出、本月一次性事件支出、到期月供、可选支出。现金不够时先压缩可选支出至 0；仍不足时停止本局，记录未覆盖缺口，不暗中借款、透支、卖出资产或跳过到期账单。
5. **目标投入。** 在支付上述项目后，计划投入以可用余额为上限，再受策略对应的安全垫下限约束。`实际投入 = min(计划投入, max(0, 支付后现金 - 安全垫下限))`。投入是可动用现金转入目标资金，不是新增财富。实际投入小于计划时记录 `CONTRIBUTION_PAUSED`，不能在文案里说“仍按原计划投入”。
6. **更新负债与目标。** 每笔负债余额最多减少本月实际支付额。现有负债字段不足以拆分利息与本金，v1 不自行推算利率；以“月供全部冲减余额”的简化假设参与本局，并在开局说明。目标资金增加实际投入，目标金额可由明确事件调整。
7. **生成月账本与检查点。** 保存期初现金、收入、各项支出、月供、计划/实际目标投入、期末现金、目标资金、债务余额、触发事件、风险标记。出现未覆盖缺口立即以 `CASH_GAP` 结束；到目标月份末以目标是否足额决定结局；重大事件可使年度推进提前暂停展示。

### 策略与安全垫

这是**模拟中的自动策略**，不是投资建议：`GOAL_FIRST` 保留 0 个月安全垫，`BALANCED` 保留 3 个月，`SAFETY_FIRST` 保留 6 个月。安全垫基数取当月“必需支出 + 到期月供”；可选支出不进入最低生存基数。若期初现金已低于安全垫，本月目标投入为 0，先恢复现金。界面须显示本局使用的策略和安全垫金额；若要与现有 Plan A/B/C 自动对应，A/B/C 分别对应目标优先/平衡/安全优先，但用户可以在开局切换模拟策略，切换后另建新局。

### 风险和停止规则

- `LOW_RESERVE`：期末现金低于本月 3 倍“必需支出 + 月供”。这是提示标记，不代表真实风险概率。
- `GOAL_AT_RISK`：按当前实际投入延续到目标月，目标资金会小于目标金额；只做等额延续算术，不含投资回报假设。
- `UNFUNDED_GAP`：压缩可选支出后仍无法足额支付刚性需求。期末现金停在 0，差额记为 `unfundedGapMinor`，本局以 `CASH_GAP` 结束，不能负现金继续推进。
- 目标提前达到也继续推进到目标月，以检查后续冲击；目标资金不会因为超过目标而自动退回现金。目标到期不足写 `GOAL_SHORTFALL`，足额写 `GOAL_MET`。
- 目标终点超过 240 月的情况不开局；不构造“无限人生”。

## 4. 事件卡规则

事件库是带版本的静态内容。`EventDefinition` 定义候选条件和效果，`EventOccurrence` 保存这一局实际触发的事件与已解析金额。二者分开，避免编辑事件库后历史剧情变化。

| 字段组 | 用途 |
|---|---|
| `origin` | 确定节点、用户确认、条件事件、探索事件 |
| `earliestMonth/latestMonth` | 适用时间窗；为空代表无此限制 |
| `conditions/exclusions` | 结构化资格判断，禁止将任意代码或 AI 文本作为可执行条件 |
| `priority` | 多个条件事件同时合格时的确定性顺序 |
| `weight` | 合格探索事件之间的抽取权重，不代表现实概率 |
| `cooldownMonths/maxOccurrences/exclusiveGroup` | 限制重复和互斥故事 |
| `effects` | 一次性支出、限时收入变化、限时支出变化、目标金额变化、其他资产价值变化或状态标签 |
| `followUpTags` | 使后续事件有条件可触发，构成事件链 |
| `narrativeKey` | 指向独立文案模板，计算器不依赖文案运行 |

同一月份所有到期的确定/用户确认事件都必须执行；条件事件按配置优先级与 ID 稳定排序，v1 每月最多一个。探索事件每自然年最多一个重大事件，且距上个探索重大事件至少 3 个月；事件池必须有“无事件”选项，让平稳年份可能出现。先筛资格、互斥、冷却和次数限制，再用固定种子从合格池抽取。v1 候选按事件 ID 排序，权重须为正整数，“无事件”权重固定为 3；随机数生成器和抽取顺序须写入 `engineVersion`，不能使用未播种的 `Math.random()`。没有合格事件就平稳推进。**禁止为了让剧情精彩而强塞疾病、失业或市场波动。**

`conditions` 中的条件全部满足才合格，`exclusions` 中任意一条满足即排除。持续 `N` 个月的效果包含触发当月，至第 `N` 个月末结束；`durationMonths: null` 的状态标签持续到本局终点。冷却期从上次发生的**次月**算起。探索池抽取之前先执行当月必然/用户确认事件并更新状态，因此同月的候选资格使用更新后的状态。

开局暂只允许事件库中有财务影响且有可靠金额模板的事件。医学诊断、婚恋关系、升迁等敏感或无法由底账推断的事实不能由 AI 直接生成；可用用户确认的宽泛事件标签（如“家庭开支增加”）。市场事件只影响明确属于该类的资产，不能对全部现金和目标资产同时扣减。

## 5. 数据实体与持久化边界

类型定义位于 [`src/domain/financial-life-simulation.types.ts`](../src/domain/financial-life-simulation.types.ts)。v1 的实体关系为：

```text
SimulationOpening（不可变开局）
       │
       └── SimulationRun（版本、种子、状态）
                 ├── SimulationTurn[]（一次点击得到的时间段）
                 │      ├── MonthlyLedger[]（逐月账本）
                 │      └── EventOccurrence[]（本局实际发生的事件）
                 ├── SimulationState（当前可继续推进的状态）
                 └── SimulationEnding（结局，未结束则为空）

EventDefinition[]（独立版本化的事件库）

ScenarioScript（比较方案时共享的外生事件脚本）
       └── SimulationComparison（关联 A/B/C 的模拟局）
```

| 实体 | 必须保存的内容 | 不应混入的内容 |
|---|---|---|
| `SimulationOpening` | 底账及方案版本、确认过的开局数字、目标资金口径、假设来源 | 当前底账对象引用；未来会变的实时值 |
| `SimulationRun` | 模式、策略、种子、引擎和事件库版本、状态 | 模型自由生成的事实 |
| `SimulationState` | 下一月计算所需余额、收入支出、有效效果、标签与事件历史 | 仅供展示的故事文本 |
| `MonthlyLedger` | 月度每个金额流向及风险标记 | 无出处的概率或收益率 |
| `EventOccurrence` | 事件 ID/版本、发生月份、实际效果、假设来源与触发链 | 可随事件库更新而变化的未解析模板 |
| `SimulationTurn` | 一次点击覆盖的月份、状态前后、事件和停顿原因 | 与月账本矛盾的另算数字 |
| `SimulationEnding` | 结局类型、目标金额/缺口、最低现金、关键事件 | “人生成功/失败”等价值判断 |
| `ScenarioScript` | 固定的外生事件月份、ID、版本与实际强度 | 针对每个方案重新抽取的事件 |

v1 不要求马上加数据库表。原型可在本机保留单局数据；正式多设备使用时，再把 `SimulationRun`、`SimulationTurn` 和事件发生记录持久化。无论存储位置如何，都必须保留版本和种子。金额、日期与事件显示文案从结果对象读取，不重算一个“UI 专用结论”。

## 6. 可复现与方案对比

- 同一 `SimulationOpening`、种子、引擎版本、事件库版本，逐月账本与事件序列必须一致。
- 重跑 Plan A/B/C 时，“同事件比较”模式先生成并冻结一份**外生事件脚本**（发生月份、事件 ID、强度）；三个方案共享该脚本。若某方案不满足事件资格，则标记该事件为“不适用”，不能暗中重抽更好的或更坏的事件。条件衍生事件可以不同，并明确标出它由方案状态差异引起。
- 不同策略或用户确认参数一律创建新局；不能修改已发生的历史回合。
- 随机种子仅决定故事抽取，不能改变确定账单、日期或用户输入金额。

## 7. 一段验算样例

假设月初可动用现金 20,000 元，月收入 10,000 元，必需支出 5,000 元，可选支出 1,000 元，月供 1,000 元，计划目标投入 2,000 元，无本月事件。`BALANCED` 的安全垫是 `3 × (5,000 + 1,000) = 18,000` 元。支付日常支出后现金为 23,000 元，因此实际投入 2,000 元，月末现金 21,000 元；目标资金增加 2,000 元。若本月再有一次性支出 8,000 元，支付后现金为 15,000 元，本月实际目标投入为 0，标记暂停投入与低储备。两种情况的期末现金都不能从目标资金中重复取用。

## 8. 实现前验收口径

1. 可以从同一快照、同一种子生成完全相同的月账本、事件和结局。
2. 月账本恒满足：`期末现金 = 期初现金 + 收入 - 必需支出 - 可选支出 - 事件支出 - 月供 - 实际目标投入`；不得小于 0。
3. 目标资金只随实际投入和明确的目标资金事件变化；月供不会超过对应负债余额。
4. 现金不够时先压缩可选支出，再暂停目标投入；仍不足则结束为现金缺口，不生成虚构借款。
5. 缺项、目标资金口径未确认、方案过期、非法金额或无效日期会阻止开局，并准确指出原因。
6. 事件条件、互斥、冷却、次数、持续期与后续链可逐项核对；无条件事件不会误触发。
7. 用户始终能分辨“底账事实”“用户确认假设”“事件库假设”和“程序计算结果”。

## 9. 已知与现有实现的衔接

现有 [`life-financial-simulation.ts`](../src/domain/life-financial-simulation.ts) 是单事件压力测试，可继续作为 `SPECIFIED_SCENARIO` 的参考实现，但不能直接充当多事件人生引擎。现有 `ScenarioResult` 表保存旧版固定压力测试结果；新模拟的数据契约先独立命名，避免覆盖历史语义。正式接入前应修正旧实现的事件月份偏移问题，并明确 `Goal.preparedAmountMinor` 与目标绑定资产的去重口径。
