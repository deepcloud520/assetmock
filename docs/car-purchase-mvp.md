# 买车决策与月度维护 MVP

## 入口与试用

从「财富总览」的“我想买车，先看看能承担多少”，或「未来规划 → 买车决策」进入。预算可留空，先确认必要资料并反推预算范围，再选择预算比较全款与贷款。已有记录可以继续维护。

建议试用顺序：更新财务底账 → 新建决策草稿 → 确认现金流、资金来源与保护边界 → 计算 → 核对并采纳 → 查看执行行动 → 本月复盘。购车完成后，使用“确认实际购车”，先预览账户变化，再确认入账。已经手工记录过同一笔购车的用户不能再次使用该入账操作。

## 本次优化

- 计算独立于 AI；AI 仅提取明确表达的资料、追问和解释，失败时保留确定性结果。
- 金额使用整数分；两种贷款还款方式逐月计算，并处理零利率、最后一期尾差和贷款费用。
- 当前月以确认的资产余额为起点，不把尚未存下的账面结余当成资产；未来按月检查资金到期、购车支出、债务和储备底线。
- 不自动猜测非活期资产的到期日；未确认的零值和缺失资料会阻止正式采纳。
- 其他目标的已准备金额与关联资产明确核对，避免重复占用。原未来规划的债务还款重复计入已修正。
- 按期方案可行时不再重复展示同一预算、同一时间的替代卡片；不可行时才提供降低预算或延期方案。
- 同一工作区首版仅允许一份筹资中的购车方案，防止多个目标重复使用同一份未来收入。
- 采纳时创建正式目标、不可变方案版本、部分资金预留及行动；不改变实际资产，也不提前建立实际贷款。
- 资料版本、计算月份和复盘版本均参与校验。采纳及购车确认使用事务和版本条件，重复请求不会重复占用或扣减资金。
- 复盘用实际余额限制可用于购车的资金；已经反映在实际支出中的消费削减不再加算。新方案需要明确确认，原方案与调整原因保留。
- 实际购车先展示每个账户的前后余额，确认后记录真实资产和负债，结束筹资任务，继续维护实际月供与养车支出。

## 模块与数据

- `src/domain/car-planning.ts`：资料校验、贷款表、逐月资金计算、可负担预算、四个专业评估模块。
- `src/server/car-planning.ts`：工作区隔离、底账与目标核对、事务采纳、月度复盘、实际购车与 AI 降级。
- `src/components/car-planning-view.tsx`：统一决策入口、方案比较、确认与维护。
- `CarDecision`：可缺资料的草稿、对话、当前方案及实际购车记录。
- `CarPlanVersion`：不可变的方案、资料和计算快照。
- `CarFundingReservation`：资金用途预留，不修改真实余额。
- `CarMonthlyReview`：月度实际情况、影响、调整确认与历史。

接口位于 `/api/car-decisions`，包括保存、计算、采纳、复盘、对话、购车预览和购车确认。沿用现有 `X-Workspace-Id` 约定。

## 计算边界

购车按所选月末发生，新增月供与养车费用从次月开始。当前月份不预估新增结余。现有债务按当前还款额保守地持续预留，直到用户更新底账并复盘，不自动推测结清时间。不用投资收益弥补缺口。贷款报价缺失时只能试算；正式采纳需要确认名义年利率口径、期限、首付、额度、还款方式和费用。

保障模块整理现有信息和保费承诺，不宣称保障充分。四个专业模块共享同一份资料，首版不新增四套独立对话产品。

仅供现有匿名工作区内的小范围可信试用。公开发布前仍需独立完成身份认证、权限、部署和数据保护工作；没有接入真实交易、支付、银行同步或贷款产品推荐。
