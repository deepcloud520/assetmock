# AI 资产管家 MVP 实施计划

## 1. 成功定义

MVP 要验证用户是否愿意提供完整财富与目标信息，以及系统是否能给出明显优于单账户工具的、可解释且可执行的决策支持。首个可发布版本必须让用户完整走通：

> 建立画像 → 录入财富底账 → 看懂总览和 Top 3 风险 → 创建目标 → 比较三套方案 → 运行压力测试 → 获得并管理行动

### 建议的产品指标

- **核心激活**：完成画像、至少录入 2 类资产和 1 项负债/收支，并查看诊断。
- **价值到达**：激活用户中成功创建目标并生成方案的比例。
- **决策参与**：生成方案用户中完成比较并选定方案的比例。
- **行动转化**：选定方案用户中接受至少一项行动的比例。
- **可信度护栏**：系统数字计算错误为 0；无证据 AI 结论率为 0；`UNKNOWN` 正确呈现率 100%。

不在首版设置资产规模、收益率或交易额作为成功指标，避免激励产品做不适当推荐。

## 2. 交付路线（建议 8 周）

### M0｜基础设施与口径冻结（第 1 周）

- 确认主币种、金额精度、家庭/个人数据归属和登录方式。
- 建立 PostgreSQL/Prisma、迁移、种子数据、CI、预览环境与错误监控。
- 定义 API contract、数据来源、版本字段、审计事件和 stale/recalculation 状态机。
- 把 PRD 所有公式整理为可执行测试样例；冻结财富健康度 v1 规则版本。

**退出条件**：CI 执行 lint/typecheck/unit/build；测试库可重建；口径决策有记录。

### M1｜画像与财富底账（第 2–3 周）

- PAGE-01：基础信息、收入支出、直接选择风险等级；失败保留输入。
- PAGE-02：资产/负债/收入/支出的新增、编辑、删除与二次确认。
- 即时计算总资产、总负债和净资产；实现四账户映射。
- 支持正常、空、部分、错误状态；写操作生成审计事件和埋点。

**退出条件**：CRUD 与核心金额规则验收通过；自住房默认排除；目标绑定优先于增长账户。

### M2｜规则引擎、总览与诊断（第 4 周）

- 实现应急覆盖、负债率、偿债负担、短债覆盖、Largest/Top3/HHI 与流动性阶梯。
- 实现五维加权健康分；不可计算规则为 `UNKNOWN` 并重新归一权重。
- PAGE-03 首屏展示净资产、健康度、四账户、Top 3 风险和目标概览。
- PAGE-04 展示结论、证据、涉及数据、影响和建议方向；AI 失败时规则结果仍可用。

**退出条件**：边界值、零分母、缺失数据、负净资产和极端金额测试全部通过。

### M3｜人生目标与三方案（第 5–6 周）

- PAGE-05 完成目标 CRUD、资产绑定、覆盖率、资金缺口、期限与健康状态。
- 目标金额由 AI 提议时明确标识 `AI_GENERATED`，必须经用户确认后成为规划输入。
- PAGE-06 展示当前路径和目标优先/平衡/安全优先三套方案。
- AI 只提出候选约束；规则引擎复算所有金额和指标；用户可选定一个版本化方案。

**退出条件**：三方案均能说明完成情况、月投入、配置、风险、流动性、改变、获得与牺牲；上游修改使其立即 `STALE`。

### M4｜压力测试与行动闭环（第 7 周）

- PAGE-07 实现权益跌 30%、收入中断 3 个月、购房成本涨 10% 三个确定性场景。
- 防重复提交；展示前后净资产、流动性、目标完成度、风险变化与重规划判断。
- PAGE-08 从选定方案生成带金额、优先级、期限和依赖的行动。
- 实现行动状态机，`USER_MARKED_COMPLETED` 不写底账；底账变化满足验证规则后才进入 `VERIFIED_COMPLETED`。

**退出条件**：三种场景的 golden tests 与行动状态迁移测试通过。

### M5｜稳定性、合规表达与灰度（第 8 周）

- 覆盖全局六状态、AI 超时/格式错误/数据缺失/无目标等异常路径。
- 可访问性、移动端、性能、安全、备份恢复与隐私检查。
- 完成核心旅程 E2E、埋点验收和小流量灰度；准备用户反馈入口与回滚方案。

**退出条件**：P0 验收清单全部通过，无阻断级缺陷，数字口径由产品与工程共同签字。

## 3. 优先级与切片原则

每个里程碑按“数据模型 → 确定性规则 → API → 状态齐全的 UI → 埋点 → 测试”纵向交付。P0 不引入产品搜索、复杂收益指标、历史方案浏览或自由对话；它们只有在核心闭环数据证明价值后进入 P1。

## 4. 测试策略

| 层级 | 重点 |
| --- | --- |
| 单元 | 所有 BR 公式、阈值边界、四账户冲突、评分归一、状态机 |
| 属性测试 | 金额不丢精度、汇总守恒、健康分始终 0–100、缺失维度不被误判 |
| 集成 | 写底账与 stale 标记原子性、版本防旧结果覆盖、AI schema/事实校验与降级 |
| E2E | 首次使用完整链路、编辑后重算、无目标、部分数据、AI 超时、删除确认 |
| 人工验收 | 中文可读性、解释是否包含证据/影响/建议、方案取舍是否中立 |

核心公式采用由产品确认的固定输入/输出样例作为 golden tests。任何公式或阈值变化必须提升 `formulaVersion`，旧快照继续可追溯。

## 5. 主要风险与缓解

| 风险 | 缓解措施 |
| --- | --- |
| 用户不愿录入完整资产 | 渐进录入、明确用途、支持稍后补充，先用 PARTIAL 提供有限价值 |
| AI 生成错误数字或事实 | 规则引擎掌握数字；结构化输出、引用校验、用户确认与明确来源标签 |
| 方案看似专业但不可执行 | 每套方案必须满足现金流、期限、流动性和可调整资产约束 |
| 修改数据后展示旧建议 | 事务内标记 STALE、结果版本检查、页面显著提示、幂等重算 |
| 财务数据泄露 | 最小采集、服务端密钥、传输/静态加密、脱敏日志、删除与导出机制 |
| 用户将工具理解为收益保证 | 固定风险披露、概率与收益禁语、情景明确为压力测试而非预测 |

## 6. 开发前仍需产品冻结的决策

以下问题不阻碍工程骨架和规则原型，但必须在 M0 结束前确认：

1. 产品首发地区、适用监管辖区及支持币种；若只有人民币，应明确拒绝还是暂存外币资产。
2. 账户模型是单用户、家庭共享还是“用户拥有一个家庭财富空间”；这会影响权限和数据归属。
3. “保险基础保障情况”的最小字段，以及哪些项目计入保障账户但不计入总资产。
4. 目标金额由 AI 推演时所需的假设（通胀率、城市/房屋信息、退休年龄等）及用户确认流程。
5. Plan A/B/C 的可用资产范围、再平衡成本、最低安全垫和禁止调整资产的硬约束。
6. 财富健康分对“没有目标”的处理：目标维度排除并归一，还是提示完成目标设置后才给总分。建议采用前者并标注置信/完整度。

## 7. Definition of Done

一项功能只有在以下条件全部满足时才完成：需求与异常状态已实现；规则有边界测试；AI 内容有 schema、来源与降级；上游修改能正确触发 stale；无敏感日志；埋点可验证；键盘和移动端可用；文案不承诺收益；相关技术文档已更新。
